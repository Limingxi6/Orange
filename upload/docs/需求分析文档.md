## 2. 业务背景与目标

### 2.1 业务背景

“橘源通”服务于柑橘种植到销售全链路，核心场景是：

1. 生产过程数字化（批次、日志、病害、天气、风险）。
2. 品控和定价数字化（分级、价格区间、风险提示）。
3. 消费端信任建立（二维码溯源、校验、可选链上锚定）。

### 2.2 核心业务目标

1. 降低记录门槛：种植户可在小程序完成核心操作。  
2. 强化过程闭环：病害结果、天气、日志可汇聚为风险评估。  
3. 输出可执行决策：分级结果+价格区间+风险提示可直接用于销售动作。  
4. 提供可验证追溯：消费者扫码可查看并校验关键生产信息。

### 2.3 MVP 成功标准（业务视角）

1. 13 个页面主流程可跑通。  
2. 三条 AI 主链路（病害、分级、风险）稳定返回。  
3. 关键兼容接口字段不破坏既有前端。  
4. 外部服务失败时主流程不崩（有 deterministic fallback）。

## 3. 范围边界

### 3.1 本期纳入（In Scope）

1. 认证与用户基础查询。  
2. 批次管理。  
3. 农事日志记录与查询。  
4. 病害识别（含 AI 兼容接口）。  
5. 风险评估（摘要/评估/历史）。  
6. 果实分级与定价（规则主导，感知可回退）。  
7. 产品列表与二维码生成。  
8. 溯源详情与校验。  
9. 天气查询与缓存。  
10. 图片上传。

### 3.2 暂不纳入（Out Scope）

1. 复杂权限中心（细粒度资源权限矩阵）。  
2. token 黑名单与强制下线机制。  
3. 完整交易订单与结算系统。  
4. 大规模多租户隔离（组织级强隔离）。  
5. 全自动模型生命周期平台（训练编排、灰度、回滚控制台）。

## 4. 角色与权限需求

| 角色 | 核心诉求 | 关键功能 | 访问限制 |
|---|---|---|---|
| 种植户（farmer） | 日常生产操作高效 | 批次、日志、病害、风险、分级、二维码 | 默认仅本人业务数据 |
| 管理者（manager） | 批次级过程管理 | 批次详情、风险历史、日志复核 | 可管理所负责批次 |
| 管理员（admin） | 账号与范围治理 | `GET /api/users/:userId` 等管理能力 | 全局可见 |
| 消费者（匿名扫码） | 查询产品可信信息 | 溯源详情、校验结果查看 | 只读，不可写 |

权限规则需求：

1. 默认接口需 JWT。  
2. `@Public()` 仅用于登录与发码等免认证入口。  
3. 管理员接口需 `RolesGuard`。  
4. 本人/管理员混合场景需 `SelfOrAdmin`。

## 5. 端到端业务流程需求（主流程）

### 5.1 生产管理主流程

1. 用户登录获取 token。  
2. 创建批次或进入已有批次。  
3. 记录农事日志（施肥、浇水、喷药、巡检等）。  
4. 上传图片执行病害识别。  
5. 将识别结果写入日志与病害记录。

### 5.2 风险评估主流程

1. 系统聚合批次阶段、天气、病害、灌溉等信息。  
2. 规则引擎计算风险等级。  
3. LLM 仅润色 `reason/suggestion`，不得改级别。  
4. 风险结果落库并返回页面兼容字段。

### 5.3 分级定价主流程

1. 前端上传图片或填写结构化参数。  
2. 感知层输出质量特征（远程 AI 或本地回退）。  
3. 规则引擎输出等级与价格区间。  
4. LLM 生成解释文案（失败则回退模板）。  
5. 结果返回并可选落库。

### 5.4 溯源主流程

1. 产品生成二维码（优先小程序码，失败回退普通二维码）。  
2. 同步生成/更新 trace 快照与 proof hash。  
3. 消费者扫码查看 `/api/trace/:code`。  
4. 需要时执行 `/api/trace/:code/verify` 哈希验真。

## 7. 详细功能需求（逐功能、逐步骤）

### 7.1 认证与用户

#### FR-AUTH-001 登录 `POST /api/auth/login`

目标：让用户获得可用 JWT 并建立会话。

主流程：

1. 小程序登录页输入手机号与验证码（当前前端字段为 `phone/password` 复用）。  
2. `services/auth.login` 调用后端登录接口。  
3. 后端按手机号查用户。  
4. 密码校验：优先 bcrypt，兼容历史 pbkdf2。  
5. 校验账号状态必须是 `active`。  
6. 生成 JWT。  
7. 返回 `token + userInfo`。  
8. 前端保存 token，拉取 profile，写入缓存。

异常流程：

1. 手机号不存在或密码错误，返回业务错误。  
2. 账号禁用，返回禁止访问错误。  
3. token 缺失时，前端请求层统一踢回登录。

验收要点：

1. 返回字段含 `token`、`userInfo.userId/id/phone/nickname/avatar/role`。  
2. 之后访问受保护接口可通过鉴权。

#### FR-AUTH-002 发送验证码 `POST /api/auth/send-code`

主流程：

1. 前端输入手机号并请求发码。  
2. 后端生成 6 位码，过期时间默认 300 秒。  
3. 优先写 Redis，失败回退内存缓存。  
4. 开发环境返回 `debugCode` 便于联调。

异常流程：

1. 短时间重复发送，返回“发送过于频繁”。

#### FR-AUTH-003 获取资料 `GET /api/auth/profile`、`GET /api/users/me`

主流程：

1. 前端携带 Bearer token 调用。  
2. 后端根据 JWT 中 `sub` 查用户。  
3. 返回标准化用户信息结构。

#### FR-AUTH-004 退出 `POST /api/auth/logout`

主流程：

1. 前端调用退出接口。  
2. 后端返回 `success: true`（MVP 语义）。  
3. 前端本地清理 token/userInfo。

限制：当前不做 token 黑名单。

### 7.2 批次管理

#### FR-BATCH-001 批次列表 `GET /api/batches`

主流程：

1. 前端传 `keyword/stage/page/limit/pageSize/sort`。  
2. 后端构造 Prisma `where`。  
3. 执行分页查询和 count。  
4. 返回 `list/total/page/pageSize`。

兼容要求：`limit` 与 `pageSize` 均可用。

#### FR-BATCH-002 批次详情 `GET /api/batches/:id`

主流程：

1. 校验 `id`。  
2. 查询批次并统计 `farmingLogs/products` 数量。  
3. 返回详情 + `logsCount/productsCount`。

#### FR-BATCH-003 创建批次 `POST /api/batches`

主流程：

1. 前端提交 `batchNo? orchardName variety plantingDate ...`。  
2. 后端确定 `managerId`（默认当前用户）。  
3. 校验负责人存在且可用。  
4. 如用户传 `batchNo`，校验唯一；否则系统生成。  
5. 事务创建 `batch`。  
6. 同事务自动创建默认 `product`，保证“我的产品”可见。

异常流程：

1. 负责人无效。  
2. 批次号冲突。  
3. 自动生成批次号重试失败。

#### FR-BATCH-004 阶段更新 `PUT /api/batches/:id/stage`

主流程：

1. 校验批次存在。  
2. 更新 `stage/updatedAt`。  
3. 返回 `success:true`。

### 7.3 农事日志

#### FR-LOG-001 日志列表 `GET /api/logs`

主流程：

1. 必填 `batchId`。  
2. 后端先校验批次是否存在。  
3. 查询日志并关联操作人。  
4. 组装页面友好字段：`time/operator/detail/images`。

#### FR-LOG-002 新建日志 `POST /api/logs`

主流程：

1. 兼容输入：`batchId/batch_id`、`type/log_type`、`content/description`、`images/image_url`。  
2. 后端校验必填项。  
3. 校验批次存在。  
4. 写入 `farming_logs`。  
5. 返回标准日志对象。

#### FR-LOG-003 类型字典 `GET /api/logs/types`

返回固定枚举，用于前端筛选与录入。

### 7.4 病害识别

#### FR-DIS-001 病害预测 `POST /api/disease/predict`

主流程：

1. 输入：`file` 或 `imageUrl`，必有其一；`batchId` 可传。  
2. 若未传 `batchId`，后端尝试取当前用户最近批次。  
3. 图片上传走 `upload` 模块，得到可访问 URL。  
4. 调 `DiseaseInferenceClient`：
   1. 优先远程 AI 接口。  
   2. 失败或配置缺失时回退本地规则推理。  
5. 计算 `needManualReview`。  
6. 调 `AiNarrativeService.explainDiseaseResult` 生成建议（失败回退 deterministic 文案）。  
7. 落库 `disease_records`。  
8. 返回识别结果。

#### FR-DIS-002 兼容预测 `POST /ai/disease/predict`

需求：保留历史调用路径与字段。

兼容输出必须包含：

- `label`
- `confidence`
- `severity`
- `advice`
- `needManualReview`
- 兼容图像字段 `image_url`

#### FR-DIS-003 识别记录 `GET /api/disease/records`

支持按 `batchId` + 分页查询。

### 7.5 风险预警

#### FR-RISK-001 风险摘要 `GET /api/risk/summary`

主流程：

1. 有 `batchId` 则单批次；否则取当前用户最近批次。  
2. 查询历史风险记录。  
3. 若无记录，自动对最多 5 个批次执行即时评估并落库。  
4. 返回 `total/high/medium/low/latestList`。

#### FR-RISK-002 风险评估 `GET /api/risk/assessment`

主流程：

1. 聚合数据：批次阶段、天气缓存、近 7 天病害、最近灌溉日志。  
2. 规则引擎计算 `overallLevel/riskItems/suggestions`。  
3. LLM 润色 `reason/suggestion`。  
4. 落库 `risk_records`。  
5. 返回评估结果。

#### FR-RISK-003 风险历史 `GET /api/risk/history`

兼容参数：`batchId/batch_id` + `page/pageSize/limit`。

#### FR-RISK-004 兼容路径 `GET /api/risk/:batchId`

需求：行为与 `assessment` 一致，保证旧前端不改路径也能运行。

稳定字段：`level/levelText/reason/suggestion`。

---

### 7.6 果实分级与定价

#### FR-PRICE-001 AI 分级 `POST /ai/fruit/grade`

主流程：

1. 接收文件或 JSON（兼容 `packageType/packaging`、`batchId/batch_id`）。  
2. 输入归一化（渠道、包装、数值区间）。  
3. 调感知层：
   1. 优先 `FruitInferenceClient` 远程感知。  
   2. 失败回退本地感知规则。  
4. 合并特征后进入规则引擎：
   1. 计算等级（A/B/C）。  
   2. 计算零售/批发价格区间。  
5. LLM 生成解释文案。  
6. 可用时落库 `fruit_grade_records`。  
7. 返回前端依赖字段。

稳定输出字段（必须保持）：

- `variety`
- `grade`
- `colorScore`
- `defectRatio`
- `sizeScore`
- `maturityScore`
- `retailMinPrice`
- `retailMaxPrice`
- `wholesaleMinPrice`
- `wholesaleMaxPrice`
- `reason`
- `riskWarning`
- `factors`

#### FR-PRICE-002 规则分级 `POST /api/price/grade`

需求：无图场景支持结构化输入直接走规则计算。

#### FR-PRICE-003 基准价 `GET /api/price/baseline`

需求：给前端展示地区/品种基准信息。

#### FR-PRICE-004 定价建议 `GET /api/price/suggestion`

需求：支持 `batchId` 或直接传等级参数查询建议价。

### 7.7 产品二维码与溯源

#### FR-PROD-001 产品列表 `GET /api/products`

主流程：

1. 进入列表前自动补全“无产品批次”的默认产品。  
2. 按 `batchId/grade/status` 查询并分页。  
3. 返回批次信息、二维码是否生成状态。

#### FR-PROD-002 生成二维码 `POST /api/products/:id/qrcode`

主流程：

1. 校验产品存在。  
2. 生成 `traceCode`（可接受前端自定义）。  
3. 生成二维码：
   1. 优先微信小程序码。  
   2. 失败回退普通二维码。  
4. 更新产品 `qrCodeUrl`。  
5. 调 `TraceService.createOrUpdateForProduct` 同步快照与 proof。  
6. 返回 `qrcodeBase64/qrcodeType/qrcodeFallback` 等字段。

---

### 7.8 溯源详情与校验

#### FR-TRACE-001 溯源详情 `GET /api/trace/:code`

主流程：

1. 支持 traceCode 与数字 productId。  
2. 无 trace 记录时可按产品自动生成。  
3. 聚合产品、批次、日志、病害形成快照。  
4. 返回 `proofType/proofHash/verified/anchorStatus` 等信息。  
5. 附加 LLM 溯源文案（失败回退模板）。

#### FR-TRACE-002 溯源校验 `GET /api/trace/:code/verify`

主流程：

1. 读取 trace 快照重算 hash。  
2. 与存储 `proofHash` 比对。  
3. 兼容历史占位 hash 时可自动修复重建。  
4. 更新 `verified/verifyMessage/verifiedAt`。  
5. 返回校验状态与锚定信息。

校验原则：本地 hash 验证是主判定，链上锚定仅做增强证据。

---

### 7.9 天气与上传

#### FR-WEA-001 当前天气 `GET /api/weather/current`

主流程：

1. 参数兼容 `regionCode/region_code/city`。  
2. 先查 `weather_cache`（当日维度）。  
3. 缓存命中直接返回。  
4. 未命中调 provider（real/mock）。  
5. 回写缓存并返回。

#### FR-WEA-002 天气预报 `GET /api/weather/forecast`

1. `days` 默认 15，最大 15。  
2. 同样优先读缓存，未命中拉 provider。  
3. 返回目标天数切片。

#### FR-UP-001 图片上传 `POST /api/upload/image`

主流程：

1. 校验文件存在。  
2. 校验大小（默认 10MB）。  
3. 校验类型（jpeg/png/webp）。  
4. 按 `UPLOAD_MODE` 选择存储实现。  
5. 返回 URL 与文件信息。

## 9. 非功能需求

### 9.1 一致性

1. 后端统一响应：`{ code, message, data }`。  
2. 统一鉴权头：`Authorization: Bearer <token>`。  
3. 稳定接口字段不得随意删除或改语义。

### 9.2 安全

1. JWT + 守卫（默认受保护）。  
2. 输入参数 DTO 校验。  
3. 日志脱敏：不得泄露 API Key、私钥、密码。

### 9.3 可用性与容错

1. AI 不可用时回退本地规则。  
2. LLM 失败时回退 deterministic 文案。  
3. 天气 provider 失败时可切 mock。  
4. 锚定失败不影响本地验真结论。

### 9.4 可维护性

新增配置必须同步：

1. `backend/.env.example`  
2. `backend/src/config/configuration.ts`  
3. `backend/src/config/env.validation.ts`

### 9.5 可追溯性

关键链路应记录：

1. 请求标识（如 `requestId`）。  
2. 模型版本（`modelVersion`）。  
3. 来源字段（`source.engine/decision`）。

## 10. AI 与 LLM 边界需求（强约束）

1. 传统模型/规则必须负责：
   1. 病害分类。  
   2. 分级计算。  
   3. 风险等级计算。
2. LLM 只允许负责：
   1. 解释。  
   2. 建议。  
   3. 问答与文案。
3. 农业建议要求保守表达，低置信度必须提示不确定性。
