# 橘源通小程序：农事日志对区块链溯源的辅助作用与创新设计

更新时间：2026-04-23

## 1. 文档目的

本文聚焦一个核心问题：在“橘源通”中，农事日志并不是区块链模块的附属信息，而是链下可信证据的重要组成部分。

目标是说明三件事：

1. 农事日志如何进入溯源与验真链路。
2. 农事日志对区块链存证到底提供了哪些业务价值。
3. 当前方案的创新点在哪里，以及后续如何持续演进。

## 2. 结论先行

在当前实现中，区块链并不直接存储农事日志原文，而是对包含农事日志快照在内的整体业务快照生成 `proofHash` 并进行链上锚定（可选增强）。

因此，农事日志的核心价值是：

1. 作为快照中的“过程性证据”参与哈希，支撑“可验证的生产过程完整性”。
2. 作为跨模块上下文（病害、批次、溯源）提升验真结果的可解释性。
3. 以低成本、可回退、可演进的方式实现“链下细节 + 链上摘要”的可信闭环。

## 3. 当前实现范围（事实基线）

农事日志后端接口：

- `GET /api/logs`
- `POST /api/logs`
- `GET /api/logs/types`

对应模块：

- `backend/src/modules/log/log.controller.ts`
- `backend/src/modules/log/log.service.ts`

溯源主链路：

- `GET /api/trace/:code`
- `GET /api/trace/:code/verify`
- 二维码触发生成/更新 trace 快照：`backend/src/modules/product/product.service.ts`

关键事实：

1. 链上仅锚定最小元数据：`traceCode + proofHash`（见 `TraceAnchor.sol`）。
2. 完整业务快照（含农事日志）保留链下数据库（`trace_records.logs_snapshot`）。
3. `verified` 主判定来自链下哈希比对，链上锚定为增强证据而非主流程前置条件。

## 4. 农事日志进入区块链溯源的链路

### 4.1 日志采集（链下事实采集层）

农事日志来源至少包括两类：

1. 手工日志：小程序 `pages/farming-log-create` 提交 `POST /api/logs`。
2. 自动日志：病害识别页 `pages/disease-recognize` 一键保存识别结果为农事日志。

落库字段核心包括：

- `batchId`
- `type`
- `content`
- `operationDate`
- `images`
- `operatorId`

对应表：`farming_logs`（Prisma: `FarmingLog`）。

### 4.2 快照聚合（溯源证据构建层）

生成 trace 记录时，`TraceService.buildAggregate` 会聚合同一批次下：

1. 批次信息 `batchInfo`
2. 农事日志时间线 `logTimeline`（来源 `farmingLog.findMany`）
3. 病害记录 `diseaseRecords`

随后在 `generateAndPersistTraceRecord` 中写入：

- `batchSnapshot`
- `logsSnapshot`（农事日志快照）
- `inspectionsSnapshot`

并基于快照计算 `proofHash`。

### 4.3 哈希与锚定（可信证明层）

`createContentHash` 采用：

1. 对对象键排序（稳定序列化）
2. `JSON.stringify`
3. `sha256`

得到稳定 `proofHash`，用于：

1. 链下验真主判定（`verifyProof`）
2. 可选链上锚定（EVM / Notary / Hash provider 策略）

### 4.4 前端验真展示（信任可视化层）

小程序溯源页展示：

- `proofHash`
- `anchorStatus`
- `txId`
- `chainProvider`
- `chainNetwork`
- 校验结果 `verified/status/message`

并支持主动触发 `/verify` 复验。

## 5. 农事日志对区块链的辅助作用（业务价值拆解）

### 5.1 作用一：把“结果可信”扩展为“过程可信”

只对最终产品结果存证，最多证明“现在的数据状态”；加入农事日志后，可以证明“这个状态的形成过程”也参与了证据摘要。

价值：

1. 降低“只看终态、忽略过程”的可信盲区。
2. 为监管/采购方提供过程侧核验抓手。

### 5.2 作用二：提供时间轴证据，增强可审计性

农事日志天然是时间序列数据（`operationDate` + `type` + `content`）。进入 `logsSnapshot` 后，哈希可覆盖“时间+行为+描述”组合。

价值：

1. 支撑“某批次在某阶段做过哪些关键操作”的可追述。
2. 在争议场景中提供可复核证据基础。

### 5.3 作用三：连接 AI 识别与人工作业，形成闭环证据链

病害识别结果可自动写入农事日志（`source: disease_recognize`），使“检测 -> 记录 -> 溯源存证”形成闭环。

价值：

1. 避免识别结果停留在单点页面，不进入长期可信资产。
2. 提升链下证据的连续性与解释能力。

### 5.4 作用四：作为跨模块公共事实层，降低数据孤岛

同一批次的日志可被：

1. 溯源模块用于快照与验真
2. 风险模块用于规则判断上下文（例如灌溉相关日志）
3. 批次详情与“我的”页面用于运营视图

价值：

1. 一次采集，多模块复用。
2. 减少“各模块各记一份”的一致性问题。

### 5.5 作用五：支撑“链下详单、链上摘要”的低成本可信架构

农事日志通常包含文本、图片等高体量内容，不适合全量上链。当前方案将其保留链下，仅将聚合结果摘要上链。

价值：

1. 降低链上存储与 Gas 成本。
2. 避免敏感原文直接上链的合规风险。
3. 保留验真能力（链下重算哈希与链上摘要比对）。

## 6. 创新点（结合当前代码实现）

### 6.1 创新点一：农事日志作为“可验证输入”而非“展示附件”

很多系统把日志仅用于页面展示；当前实现把日志纳入 `logsSnapshot -> proofHash`，让日志直接影响验真结果。

创新价值：

1. 把“日志”从 UI 信息升级为可信计算输入。
2. 让过程数据具备技术上的不可抵赖性基础。

### 6.2 创新点二：稳定哈希策略支撑跨环境复验

通过对象键排序 + `sha256`，降低 JSON 键顺序差异带来的哈希抖动。

创新价值：

1. 提升“同快照同摘要”的可复现性。
2. 为后续第三方核验接口打基础。

### 6.3 创新点三：非阻塞锚定，主流程高可用

锚定失败仅反映在 `anchorStatus`，不直接推翻链下哈希主判定。

创新价值：

1. 外部链路异常不阻断核心业务。
2. 适合农业场景下网络与基础设施不稳定的现实条件。

### 6.4 创新点四：可插拔锚定提供方，降低技术路径锁定

Provider 已抽象为 `hash / evm / notary`，可以按配置切换。

创新价值：

1. 支持从 PoC 到生产的渐进演进。
2. 避免被单一链平台或服务商强绑定。

### 6.5 创新点五：小程序端“可理解证据”呈现

不仅返回“已上链/未上链”，还展示 `proofHash`、`txId`、`anchorStatus`、网络信息并支持复验操作。

创新价值：

1. 技术证据可被用户直接感知与操作。
2. 区块链价值从后端能力转化为前端信任体验。

## 7. 边界与约束（对外口径建议）

必须明确：

1. 农事日志参与的是“证据摘要计算”，不是“日志原文全量上链”。
2. 区块链不替代病害分类、分级定价、风险打级等确定性计算逻辑。
3. `verified` 主判定基于链下哈希一致性；链上锚定是增强证据。

## 8. 风险点与治理建议

### 8.1 数据真实性风险（输入侧）

当前日志真实性依赖账号权限与业务流程，无法仅靠区块链自动判真。

建议：

1. 增加关键操作双签/审批（高价值批次）。
2. 对日志补充设备、地理、时间戳等元信息并纳入快照。

### 8.2 快照时点风险（时序侧）

若“先生成 trace 后补日志”，新日志不会出现在旧 `proofHash`。

建议：

1. 明确“每次生成二维码/上架前强制重建快照”流程。
2. 对外展示 `generatedAt` 和最近日志时间，减少误读。

### 8.3 大规模场景性能风险（工程侧）

日志量增长会提高聚合和哈希计算开销。

建议：

1. 对快照范围做可配置限制与版本化策略。
2. 将锚定流程异步任务化并增加重试与监控。

## 9. 建议的验收指标（可量化）

1. `trace verify` 成功率（按日/周）。
2. `anchorStatus=success` 占比与平均耗时。
3. 含日志快照的 trace 记录覆盖率。
4. 从日志创建到可验真的时延。
5. 用户侧复验触发率与失败原因分布。
